# 通用 MCP 客户端设计

## 目标

将 `mcp/client.py` 改造成与具体工具无关的 MCP 客户端。客户端通过命令行接收工具名和 JSON 参数，调用服务端任意已注册工具，并统一输出工具结果。

当 `mcp/server.py` 新增普通工具时，`mcp/client.py` 不需要新增对应的结果变量、分支或格式化逻辑。

## 当前问题

当前客户端虽然会调用 `list_tools()` 展示服务端工具，但随后固定调用 `add` 和 `echo`，因此客户端示例与服务端工具名称、参数结构耦合。每增加一个工具，都需要在客户端增加一次专用调用和结果输出。

## 选定方案

采用通用命令行调用入口：

```text
python mcp/client.py --list
python mcp/client.py <tool_name> [json_arguments]
```

其中 `json_arguments` 是 JSON 对象，省略时使用 `{}`。工具名和参数由运行时提供，客户端不内置 `add`、`echo` 或其他具体工具名称。

示例：

```text
python mcp/client.py add '{"a":20,"b":22}'
python mcp/client.py echo '{"text":"hello"}'
```

## 结构与数据流

1. 解析命令行参数。
2. 使用现有的 stdio 参数启动 `mcp/server.py`。
3. 创建 MCP `ClientSession` 并初始化。
4. `--list` 模式调用 `list_tools()`，输出工具名、描述和可用的输入 schema 信息。
5. 调用模式将 JSON 参数解析为对象，通过统一的 `call_tool(session, tool_name, arguments)` 调用任意工具。
6. 将 MCP 返回值交给统一的 `format_tool_result(result)`，输出格式化结果。
7. 对参数错误、工具调用错误和服务端错误返回非零退出状态。

客户端只依赖 MCP 的工具发现、工具调用和结果内容协议，不依赖某个工具的业务语义。

## 结果处理

将当前面向简单文本的结果拼接逻辑一般化为统一结果格式化函数：

- 遍历返回结果的 `content` 内容块。
- 对有 `text` 属性的内容块输出文本。
- 对其他内容块保留其可读表示，不因未知内容类型崩溃。
- 如果结果包含结构化内容，则以 JSON 形式输出，确保对象、数组和标量结果可读。
- 保留 MCP 结果中的错误状态，并由调用层以错误状态退出。

结果格式化按返回内容类型处理，不按工具名称处理。因此新增工具只要返回标准 MCP 结果，就不需要修改客户端。

## 错误处理

- 没有参数或参数 JSON 不是合法对象时，打印用法或参数错误并退出非零状态。
- 工具不存在时，保留服务端调用错误信息并退出非零状态。
- 服务端进程启动、初始化或通信失败时，打印简明错误并退出非零状态。
- 工具成功返回空内容时，客户端不抛出索引错误，输出可识别的空结果表示。

## 测试设计

新增客户端测试，避免依赖真实子进程和网络服务：

- 结果中包含文本内容块时，能够拼接并输出文本。
- 结果中包含非文本内容块时，能够输出可读表示。
- 结果包含结构化内容时，能够输出 JSON。
- 通用调用函数把命令行传入的工具名和参数原样交给 session。
- 缺省参数解析为 `{}`，非法 JSON 和非对象 JSON 被拒绝。
- 工具调用异常和错误结果返回非零退出状态。
- 客户端源代码不再固定引用 `add_result`、`echo_result` 或按工具名分支。

## 非目标

- 不修改 MCP 服务端工具的注册方式。
- 不为每个工具自动生成专用 Python 包装函数。
- 不在本次改动中实现交互式多轮工具选择。
- 不改变现有 `mcp/server.py` 中 `add`、`echo` 的行为；它们仅作为服务端现有工具保留。
