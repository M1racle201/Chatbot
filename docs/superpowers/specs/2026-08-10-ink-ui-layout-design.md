# Ink UI 排版优化设计

## 背景

当前 Ink 前端集中在 `ui/index.jsx`，使用单列内容流同时承载模式、对话、工具日志、状态、结果和输入。现有界面功能完整，但信息层级弱，日志和正文的视觉权重接近，输入区与内容区的边界也不够稳定。

本次改造参考 Claude Code 的终端界面节奏，采用“聚焦对话流”方向：让对话成为唯一主轴，把模式、任务状态和工具日志压缩成上下文层。

## 目标

- 提升终端内的阅读顺序，让用户能快速区分用户输入、AI 回复、运行日志和最终结果。
- 保留当前命令、模式切换、事件协议和后端行为。
- 在不同终端高度下保持输入区可见，长文本正常换行而不是被截断。
- 通过少量稳定的展示组件建立可维护的排版边界。

## 非目标

- 不修改 `ui/bridge.py`、Python 后端、事件字段或命令语义。
- 不新增侧边栏、持久化会话列表、复杂动画或新的 npm 依赖。
- 不改变聊天、任务、智能任务三种模式的执行流程。

## 设计

### 1. 页面结构

根容器保持纵向布局，分为三个区域：

1. `Header`：显示产品名、当前模式和忙碌状态，使用单一紧凑的顶栏承载全局上下文。
2. `Transcript`：占据主要高度，按时间顺序呈现对话和运行信息，是唯一的主内容流。
3. `Composer`：固定在底部，使用 `›` 作为输入提示符，并在空闲状态提供命令提示。

内容区根据 `process.stdout.rows` 动态计算高度，给顶部和输入区预留稳定空间。必要时通过终端 resize 事件触发重新渲染，避免窗口变化后布局停留在旧尺寸。

### 2. 信息层级

- 用户消息：使用青色 `›` 前缀和加粗内容，作为每轮交互的视觉起点。
- AI 回复：使用绿色 `AI` 前缀和普通正文，保持连续文本阅读。
- 工具日志：使用灰色、缩进和简短前缀，表达过程信息但不抢正文注意力。
- notice：使用低干扰蓝色，保留系统提示但减少与正文的竞争。
- result：在任务完成时单独增加上下间距和加粗标题，作为结果落点。
- error：使用红色前缀，保持错误的高辨识度。
- streaming：复用 AI 回复样式，末尾显示轻量光标，不引入额外 spinner。

### 3. 组件边界

在 `ui/index.jsx` 内拆分以下展示组件：

- `Header({mode, busy})`：只负责模式和运行状态展示。
- `Transcript({items, stream, status})`：负责内容区高度和消息列表渲染。
- `Message({item})`：负责单条历史消息的语义样式。
- `Composer({input, setInput, submit, mode, busy})`：负责输入提示和 `TextInput`。

事件订阅、命令解析、桥接发送和状态更新仍由 `App` 管理。组件拆分只改变展示边界，不改变数据流。

### 4. 间距与响应式行为

采用紧凑终端间距：同一条消息内部保持零到一行间距，不同消息组之间使用一行分隔，顶栏与输入区使用稳定的一行外间距。小终端优先保证输入区和最近消息可见，历史消息继续使用现有的最近 60 条窗口。

消息正文使用换行模式，避免当前 `wrap="truncate"` 对长回复造成信息损失。状态和日志保持单行优先，过长时允许终端自然裁切，不影响主要回复。

### 5. 兼容与错误处理

- `ready`、`user`、`stream`、`done`、`log`、`notice`、`status`、`result`、`error` 事件继续使用现有字段。
- 后端启动失败、后端错误、命令无效和未选择模式的提示继续显示，只调整视觉样式。
- 当模式为 `idle` 时，输入区提示用户先选择 `/chat`、`/agent` 或 `/agentic`。
- 当 `busy` 为真时，输入区保留可见但显示处理中状态，避免用户误以为界面卡死。

## 验收标准

- 启动 Ink UI 后，顶栏、对话区和输入区能形成清晰的三段结构。
- 用户输入、AI 输出、日志、结果和错误在视觉上有稳定且可预测的区别。
- 长 AI 回复在终端中换行显示，不出现主动截断。
- 调整终端窗口高度后，输入区仍保持在底部附近并可见。
- `/chat`、`/agent`、`/agentic`、`/clear_history`、`/clear_memory`、`/exit` 行为与改造前一致。
- `ui/index.jsx` 能通过现有 npm 构建命令打包，且不引入新的依赖。

## 验证计划

1. 使用 esbuild 对 `ui/index.jsx` 进行打包检查。
2. 启动 Ink UI，验证 ready 提示、模式切换和输入区渲染。
3. 通过现有 bridge 事件结构检查用户消息、流式回复、日志、结果和错误的展示路径。
4. 在窄终端和较矮终端下手动检查布局是否保持可读。
